  二、完整构建流程

  文件上传
     │
     ├─①【文档加载 & 分割】DocumentProcessorPro
     │   ├─ 按章节标题（第编/篇/章/节）粗分
     │   ├─ 再按分隔符细分（chunk_size=1024，overlap=200）
     │   └─ 清洗去重
     │
     ├─②【向量化存入 ChromaDB】
     │   ├─ rag_docs         → 原始文档片段
     │   ├─ graph_entities   → 实体（供后续寻点）
     │   └─ graph_relations  → 关系三元组
     │
     ├─③【LLM 三元组抽取】TripleExtractor（9 线程并发）
     │   ├─ 每 4 个 chunk 合并为一批发给 LLM
     │   ├─ Schema 定向抽取，只识别：
     │   │   实体: COMPONENT / SYMPTOM / ERROR_CODE / SOLUTION
     │   │   关系: CAUSES / BELONGS_TO / RESOLVES / DIAGNOSES
     │   └─ 解析返回的 JSON，校验字段完整性
     │
     └─④【建图 & 持久化】NetworkXGraphRepository
         ├─ 内存：NetworkX DiGraph（有向图）
         ├─ 剪枝：单节点最多 20 条出边
         └─ 序列化：db/knowledge_graph.json

  四、查询阶段如何使用图谱

  查询时走四步检索（ChatUseCase.py）：
  1. 向量寻点 - 从 graph_entities 找最相关的种子实体（top_k=5）
  2. 图谱发散 - 从种子实体做 BFS 扩展 2 跳，获取相关路径
  3. 原文检索 - 从 rag_docs 找相关文档片段
  4. 拼接上下文 - 三者合并后送给 LLM 生成答案

  ---
  五、注意事项

  - 首次启动时：FastEmbedEmbeddings() 会自动从 Hugging Face 下载嵌入模型（约 130MB），可通过设置 HF_HOME
  环境变量修改缓存位置
  - 降级策略：知识图谱构建失败不影响基础向量检索，文件仍标记为 EMBEDDED 状态可正常使用
  - 异步处理：知识图谱在文件上传后异步构建，不阻塞查询接口
