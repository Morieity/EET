# Feature Specification: 智能故障诊断与故障树生成系统

**Feature Branch**: `001-fault-diagnosis-tree`  
**Created**: 2026-03-24  
**Status**: Draft  
**Input**: User description: "基于 RAG 的智能故障诊断与故障树生成系统。通过对话和文档分析帮助用户定位故障并自动生成标准化故障树 JSON。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 知识库文档上传与向量化 (Priority: P1)

维保业务人员将设备手册、历史故障报告等文档上传到系统，系统自动完成文件切分、数据清洗去重，并将内容嵌入到向量数据库中，形成可检索的故障知识库。

**Why this priority**: 知识库是整个 RAG 诊断流程的基础。没有可检索的向量化知识，后续的对话诊断和故障树生成均无法执行。此用户故事是系统的最低可用前提。

**Independent Test**: 上传一份设备维修手册 PDF，验证系统返回上传成功信息；随后通过检索接口查询文档中的关键词，确认能返回相关文档片段。

**Acceptance Scenarios**:

1. **Given** 系统已启动且向量数据库可用，**When** 用户上传一份有效的文档文件，**Then** 系统对文档执行切分、清洗去重和嵌入操作，返回上传成功信息，且后续检索可命中该文档内容。
2. **Given** 用户上传一份空文件或不支持的格式，**When** 系统接收到该文件，**Then** 系统返回明确的错误提示，说明文件无效或格式不支持，不写入向量数据库。
3. **Given** 用户上传一份包含与已有知识库高度重复内容的文档，**When** 系统处理该文档，**Then** 重复内容被识别并去重，不会在向量数据库中产生冗余片段。

---

### User Story 2 - 多轮对话式故障诊断 (Priority: P2)

维保业务人员在对话框中描述故障现象（如"设备启动后温度异常升高"），系统根据意图识别判断是否涉及故障诊断场景，从知识库中检索相关文档，生成引导性提示并与用户展开多轮对话，逐步确认故障细节（如故障时间、部位、伴随现象等），积累足够的诊断语料。

**Why this priority**: 多轮对话是连接知识库（P1）和故障树生成（P3）的核心交互环节。用户通过对话完成信息补全和确认，是系统交付诊断价值的主要途径。

**Independent Test**: 在知识库中已有相关文档的前提下，用户发送一条故障描述消息，验证系统能返回基于知识库的引导性追问；继续多轮对话后，验证系统能识别信息充足并提示可以生成故障树。

**Acceptance Scenarios**:

1. **Given** 知识库中包含与用户问题相关的文档，**When** 用户输入一条故障描述，**Then** 系统检索相关文档片段，结合上下文生成引导性追问，帮助用户补充故障细节。
2. **Given** 用户正在进行多轮对话，**When** 系统判断已积累足够的故障诊断信息，**Then** 系统主动提示用户"信息已足够，是否生成故障树？"。
3. **Given** 用户输入的问题与故障诊断无关（如闲聊或超出知识范围），**When** 系统识别此意图，**Then** 系统礼貌回复并引导用户回到故障诊断场景。
4. **Given** 知识库中无相关文档，**When** 用户输入故障描述，**Then** 系统明确告知用户当前知识库中未找到相关信息，建议上传相关文档或调整描述。

---

### User Story 3 - 故障树生成（Skill 接口留空） (Priority: P3)

当多轮对话积累的诊断语料充足时，系统调用预留的故障树生成接口（Skill 模块），根据语料生成标准化的故障树 JSON 结构。若信息不足，则返回失败信号并在对话中反馈给用户，引导其继续补充。

**Why this priority**: 故障树 JSON 是系统核心产出物，但其生成逻辑的具体实现暂不定义，仅需搭建调用骨架和数据流。依赖 P2 的对话语料积累结果。

**Independent Test**: 模拟传入一组完整的诊断语料，调用故障树生成接口，验证返回的 JSON 符合预定义的故障树结构；传入不完整的语料，验证返回失败信号及缺失信息提示。

**Acceptance Scenarios**:

1. **Given** 对话过程中已积累了充足的故障诊断语料，**When** 用户确认生成故障树，**Then** 系统调用 Skill 模块的生成接口，返回符合标准结构的故障树 JSON，并展示给用户。
2. **Given** 诊断语料不足以生成完整的故障树，**When** 系统调用 Skill 模块，**Then** 接口返回失败信号及缺失信息描述，系统在对话中向用户反馈并引导其继续补充。
3. **Given** Skill 模块发生不可预期的错误，**When** 系统调用生成接口，**Then** 系统捕获错误并向用户返回友好的错误提示，不暴露内部细节。

---

### User Story 4 - 人工校准与案例入库 (Priority: P4)

用户对系统生成的故障树 JSON 进行人工审阅和修改（如调整节点、补充原因）。确认后，故障树作为案例存储，同时生成对应的文本文件，调用预留的标准化接口（Skill 模块）进行处理后，最终写入案例数据库。

**Why this priority**: 案例入库是诊断闭环的终点，为知识积累和后续复用提供保障。依赖 P3 产出的故障树 JSON。标准化接口的具体实现暂不定义，仅搭建调用骨架。

**Independent Test**: 提供一份故障树 JSON，用户通过接口修改其中节点后提交确认，验证修改后的故障树被正确持久化到案例数据库；验证同时生成了对应的文本文件并调用了标准化接口。

**Acceptance Scenarios**:

1. **Given** 系统已生成一份故障树 JSON 并展示给用户，**When** 用户修改故障树内容并确认提交，**Then** 系统保存修改后的故障树为案例，生成对应的文本文件，调用标准化 Skill 接口处理，并写入案例数据库。
2. **Given** 用户确认的故障树格式不合法（如 JSON 结构缺损），**When** 用户提交，**Then** 系统返回校验错误信息，拒绝入库并提示用户修正。
3. **Given** 标准化 Skill 接口处理失败或不可用，**When** 系统调用该接口，**Then** 系统记录失败原因，向用户提示处理失败但案例原始数据已保存，不丢失用户输入。

---

### Edge Cases

- 用户同时上传多个文档时，系统需要按顺序处理，且单个文档处理失败不影响其余文档。
- 故障树 JSON 体量超大（节点过多）时，系统需能正常处理并返回，不因数据量导致接口超时。
- 案例入库过程中系统异常中断，已确认的故障树原始数据不能丢失，需在故障恢复后可重新入库。
- 上传的文档中包含非文本内容（如纯图片页），系统需跳过无法解析的页并告知用户。

## Requirements *(mandatory)*

### Functional Requirements

**知识库构建**

- **FR-001**: 系统 MUST 支持用户上传文档文件，并自动完成内容切分。
- **FR-002**: 系统 MUST 对切分后的文档片段执行数据清洗，去除无意义内容（如空白页、乱码段落）。
- **FR-003**: 系统 MUST 对文档片段执行去重处理，与向量数据库中已有的内容进行比较，避免冗余存储。
- **FR-004**: 系统 MUST 将清洗去重后的文档片段嵌入（Embedding）到向量数据库中，供后续检索使用。
- **FR-005**: 系统 MUST 在上传完成后返回处理结果摘要，包含成功片段数、跳过/去重片段数等信息。

**多轮对话诊断**

- **FR-006**: 系统 MUST 支持用户通过对话接口输入故障描述。
- **FR-007**: 系统 MUST 对用户输入进行意图识别，判断是否属于故障诊断场景。
- **FR-008**: 系统 MUST 根据用户问题从向量数据库中检索相关文档片段，作为诊断参考上下文。
- **FR-009**: 系统 MUST 基于检索上下文和对话历史生成引导性提示（Prompt），追问用户补充故障细节。
- **FR-010**: 系统 MUST 维护当前诊断会话的多轮对话历史，确保上下文连贯性。
- **FR-011**: 系统 MUST 能判断对话中已积累的信息是否足以生成故障树，并主动提示用户。

**故障树生成（Skill 接口）**

- **FR-012**: 系统 MUST 定义故障树生成的 Skill 接口，接收诊断语料并返回故障树 JSON 或失败信号。
- **FR-013**: 故障树生成接口 MUST 返回符合预定义 JSON 结构的故障树数据（节点包含名称、类型、子节点关系等）。
- **FR-014**: 当信息不足时，故障树生成接口 MUST 返回失败信号，并附带缺失信息的描述，系统将其反馈到对话中。
- **FR-015**: 故障树生成 Skill 模块的具体实现逻辑留空，仅定义 Protocol 接口和数据契约。

**人工校准与案例入库**

- **FR-016**: 系统 MUST 支持用户对生成的故障树 JSON 进行修改（新增/删除/编辑节点）。
- **FR-017**: 系统 MUST 在用户提交修改后校验故障树 JSON 的结构合法性。
- **FR-018**: 系统 MUST 将用户确认后的故障树作为案例持久化存储到案例数据库中。
- **FR-019**: 系统 MUST 为确认的案例生成对应的文本文件。
- **FR-020**: 系统 MUST 定义案例标准化处理的 Skill 接口，接收案例数据并执行标准化处理。标准化 Skill 模块的具体实现逻辑留空，仅定义 Protocol 接口。
- **FR-021**: 案例入库过程中，若标准化 Skill 接口失败，系统 MUST 仍保存案例原始数据，不丢失用户输入。

### Key Entities

- **文档（Document）**: 用户上传的原始文件，包含文件名、上传时间、文件类型等元信息。切分后生成多个文档片段。
- **文档片段（DocumentChunk）**: 文档切分后的最小检索单元，包含文本内容、来源文档引用、在原文中的位置信息。经清洗去重后嵌入到向量数据库。
- **诊断会话（DiagnosisSession）**: 一次完整的故障诊断交互过程，包含会话标识、创建时间、状态（进行中/已完成/已生成故障树）和关联的对话历史。
- **对话消息（ChatMessage）**: 诊断会话中的单条消息，包含角色（用户/系统）、消息内容、时间戳。多条消息构成对话历史。
- **故障树（FaultTree）**: 故障诊断的结构化产出，以 JSON 形式表示。包含根节点、中间节点和叶子节点，每个节点包含名称、类型（事件/门/原因）、子节点列表。
- **案例（Case）**: 经用户确认的故障树及其关联信息，包含案例编号、故障树 JSON、关联诊断会话、确认时间、状态（待标准化/已标准化）。存入案例数据库供后续复用。

## Assumptions

- 当前阶段仅支持 PDF 格式文档上传，后续可通过新增 Loader 实现扩展其他格式。
- 故障树 JSON 结构的具体字段定义将在规划阶段确定，规格阶段仅约定其存在和基本结构（树形、节点含名称/类型/子节点）。
- 意图识别通过 LLM Prompt 工程实现，不引入独立的 NLU 模型。
- 案例数据库的存储形式（文件系统、SQLite 或其他）在规划阶段确定，规格阶段不约定具体持久化方式。
- 系统不涉及用户认证与权限管理，面向单一角色（维保业务人员）使用。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户上传一份 50 页以内的 PDF 文档后，系统在 2 分钟内完成切分、清洗去重和向量化全流程，并返回处理结果摘要。
- **SC-002**: 用户输入故障描述后，系统在 10 秒内返回基于知识库的引导性追问或诊断回复。
- **SC-003**: 经过 3-8 轮对话后，系统能正确判断信息充足并提示用户可生成故障树，准确率不低于 80%（以人工评估为准）。
- **SC-004**: 用户从发起故障描述到获得故障树 JSON 的端到端操作不超过 15 分钟（含对话交互时间）。
- **SC-005**: 用户修改并确认故障树后，案例在 30 秒内完成入库操作，确认成功率不低于 95%。
- **SC-006**: 上传重复文档时，系统去重率不低于 90%（以文档片段级别衡量）。
