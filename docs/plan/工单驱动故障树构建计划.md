# 工单驱动故障树构建 — 优化实施计划

> 核心转变：从"对话触发 → LLM 生成"改为"工单数据驱动 → 自动构建 + 专家审核"

---

## 现状基线（已实现）

| 模块 | 状态 | 说明 |
|------|------|------|
| RAG 对话 + SSE 流式输出 | ✅ | ChatUseCase + 四步检索 |
| 故障树生成（正则触发） | ✅ | FaultTreeSkill.generate / update |
| ReactFlow 图形编辑器 | ✅ | 拖放、布局、导入导出、保存 |
| 知识图谱三元组抽取 | ✅ | GraphExtractionSkill（4类实体 + 4类关系） |
| 专家学习反馈 | ✅ | ExpertLearningUseCase（树diff → 图谱） |
| 文件管理 + 向量化 | ✅ | PDF/Word/TXT/MD → Chroma |
| 上下文管理（8个算法） | ✅ | MMR去重、重排序、压缩等 |

## 阶段一：故障工单数据基础（优先级最高）

**目标**：让系统能够导入、解析、存储故障工单，并从中自动提取故障知识。

### 1.1 故障工单数据模型

新增 `WorkOrder` 领域实体（`Backend/Domain/Entities/work_order.py`）：

```
WorkOrder
├── id: str (UUID)
├── order_no: str              # 工单编号
├── device_name: str           # 设备名称
├── device_code: str           # 设备编码
├── fault_phenomenon: str      # 故障现象描述
├── fault_cause: str           # 故障原因
├── fault_category: str        # 故障分类（机械/电气/液压/控制/软件）
├── severity: str              # 严重等级（一般/严重/紧急）
├── solution: str              # 处置措施
├── occurrence_time: datetime  # 发生时间
├── resolution_time: datetime  # 解决时间
├── operator: str              # 处理人
├── status: str                # PENDING / PARSED / LINKED
├── source_file: str           # 来源文件名
├── created_at: datetime
└── raw_text: str              # 原始文本（用于非结构化工单）
```

### 1.2 工单导入与解析

新增 `ImportWorkOrderUseCase`：

- **结构化导入**：支持 Excel/CSV 批量导入（列映射到 WorkOrder 字段）
- **非结构化导入**：对自由文本工单，用 LLM 抽取结构化字段（故障现象 / 原因 / 处置）
- **导入后自动处理**：
  1. 保存工单到 SQLite
  2. 向量化工单文本 → 新建 Chroma collection `work_orders`
  3. 从工单中抽取三元组 → 写入知识图谱（复用 GraphExtractionSkill，扩展 schema）

### 1.3 工单知识图谱增强

扩展现有图谱 schema：

```
新增实体类型:
- DEVICE          # 设备
- FAULT_MODE      # 失效模式
- WORK_ORDER      # 工单节点（关联原始工单ID）

新增关系类型:
- HAS_FAULT       # 设备 → 故障现象
- ROOT_CAUSE_OF   # 根因 → 故障现象
- TREATED_BY      # 故障 → 处置措施
- RECORDED_IN     # 三元组 → 工单来源
```

### 1.4 API 端点

| 方法 | 路径 | 功能 |
|------|------|------|
| POST | `/api/work-orders` | 创建单个工单（结构化 JSON） |
| POST | `/api/work-orders/import` | 批量导入工单（Excel/CSV/文本） |
| GET | `/api/work-orders` | 列出工单（支持按设备、分类过滤） |
| GET | `/api/work-orders/:id` | 获取单个工单详情 |
| PUT | `/api/work-orders/:id` | 更新单个工单并触发重新处理 |
| GET | `/api/work-orders/device/:name/stats` | 某设备的故障统计 |
| DELETE | `/api/work-orders/:id` | 删除工单 |

**预估工作量**：领域实体 + 仓储 + UseCase + Endpoint + 前端上传页面

## 阶段二：故障本体（Ontology）骨架

**目标**：定义标准化的故障分类体系，让 LLM 生成的树对齐本体、可比较。

### 2.1 本体数据结构

新增 `FaultOntology` 配置（可用 JSON/YAML 存储在 `db/ontology/` 下）：

```yaml
fault_categories:
  - id: MECH
    name: 机械故障
    sub_types: [轴承磨损, 密封泄漏, 振动异常, 断裂, ...]
  - id: ELEC
    name: 电气故障
    sub_types: [短路, 断路, 绝缘老化, 接触不良, ...]
  - id: HYD
    name: 液压故障
    sub_types: [油液污染, 压力不足, 泄漏, ...]
  - id: CTRL
    name: 控制/软件故障
    sub_types: [传感器失效, 信号丢失, 逻辑错误, ...]

gate_rules:
  - condition: "多个独立原因中任一可导致"
    gate_type: OR
  - condition: "需要多个条件同时满足才导致"
    gate_type: AND
  - condition: "有时序要求的多原因"
    gate_type: PAND

standard_failure_modes:   # 参考 ISO 14224
  - code: FM-001
    name: 泄漏-外部
    category: MECH
  - code: FM-002
    name: 泄漏-内部
    category: HYD
  # ...
```

### 2.2 本体在生成中的应用

修改 `FaultTreeSkill`：
- Prompt 中注入相关本体片段（按设备类型过滤）
- 要求 LLM 输出节点时必须标注 `ontology_ref`（对应本体中的哪个 failure mode）
- 后处理校验：节点是否都能映射到本体

### 2.3 前端本体管理

- 简单的本体浏览/编辑页面（可后期做，初期用配置文件）
- 故障树节点上显示本体分类标签

## 阶段三：工单驱动的故障树自动构建

**目标**：核心功能。给定一个设备，系统自动从工单+知识库中构建故障树，专家审核修改。

### 3.1 新增 `WorkOrderTreeBuildUseCase`

替代现有的"对话触发"模式，流程：

```
输入: 设备名称 / 设备编码 + (可选)顶事件描述
                    ↓
        ┌──── 阶段一：故障模式聚类 ────┐
        │ 1. 按设备检索所有关联工单      │
        │ 2. 对工单故障现象做聚类        │
        │    (向量相似度 + LLM辅助归并)  │
        │ 3. 输出: 故障模式清单          │
        │    [{现象, 频次, 典型工单}]     │
        └─────────────┬─────────────────┘
                      ↓
        ┌──── 阶段二：因果关系提取 ────┐
        │ 1. 对每个故障模式:            │
        │    - 检索工单中的"原因→结果"  │
        │    - 查询知识图谱子图          │
        │    - 检索手册中的相关段落       │
        │ 2. LLM 抽取因果三元组         │
        │ 3. 输出: 因果关系网络(有向图)  │
        └─────────────┬─────────────────┘
                      ↓
        ┌──── 阶段三：故障树结构化 ────┐
        │ 1. 选择/确认顶事件            │
        │ 2. 因果网 → 故障树转换:       │
        │    - 确定门类型(AND/OR)        │
        │    - 去环、去冗余              │
        │    - 识别基本事件(叶子节点)    │
        │ 3. 对齐本体标注               │
        │ 4. 输出: 标准故障树JSON        │
        └─────────────┬─────────────────┘
                      ↓
        ┌──── 阶段四：自检与校验 ──────┐
        │ 1. 结构完整性检查             │
        │    (无孤立节点、无悬空边)      │
        │ 2. 逻辑一致性检查             │
        │    (门类型是否合理)            │
        │ 3. 覆盖率检查                 │
        │    (工单中的故障现象覆盖了多少) │
        │ 4. 输出: 检查报告 + 故障树    │
        └─────────────┬─────────────────┘
                      ↓
            保存故障树 + 推送给前端编辑器
            专家在 ReactFlow 编辑器中审核
```

### 3.2 API 端点

| 方法 | 路径 | 功能 |
|------|------|------|
| POST | `/api/fault-trees/auto-build` | 触发自动构建（输入: device_name, top_event） |
| GET | `/api/fault-trees/:id/validation` | 获取自检报告 |
| GET | `/api/fault-trees/:id/coverage` | 获取工单覆盖率报告 |

### 3.3 前端交互

- 新增「自动构建」入口（区别于对话生成）
- 构建过程分阶段展示进度（阶段一完成 → 阶段二... → 最终结果）
- 构建完成后直接进入 ReactFlow 编辑器审核
- 每个节点可查看"来源工单"列表

## 阶段四：证据链追溯与节点级交互

**目标**：让每个故障树节点都有据可查，增强可信度。

### 4.1 节点证据模型

扩展 `FaultTreeNode`：

```
FaultTreeNode (扩展)
├── ...existing fields...
├── ontology_ref: str          # 关联本体ID
├── evidence_sources: list     # 证据来源列表
│   ├── type: "work_order" | "document" | "expert" | "graph"
│   ├── ref_id: str            # 工单ID / 文档chunk ID
│   ├── content_snippet: str   # 摘要片段
│   └── confidence: float      # 置信度
└── auto_generated: bool       # 是否AI自动生成（区分AI/专家贡献）
```

### 4.2 前端证据展示

- 节点右侧挂📎图标，点击弹出证据面板
- 证据面板显示：来源工单摘要、手册原文引用、图谱路径
- 区分 AI 生成节点（蓝色边框）和专家修改节点（绿色边框）

### 4.3 节点级 AI 操作（扩展现有编辑器）

右键菜单新增：
- 「AI 展开此节点」→ 从知识库补充子节点
- 「查找相关工单」→ 检索与该节点相关的历史工单
- 「验证逻辑」→ Critic Agent 检查该子树的合理性

## 阶段五：增量更新机制

**目标**：设备变更时不重建整棵树，而是局部更新。

### 5.1 增量更新 UseCase

新增 `IncrementalUpdateUseCase`：

```
输入:
  - existing_tree_id: 现有故障树ID
  - change_description: 变更说明（新增部件/新故障案例/固件更新）
  - new_work_orders: 新增的工单列表（可选）

处理:
  1. 加载现有故障树
  2. 分析变更影响范围（哪些子树受影响）
  3. 对受影响子树：
     - 检索新工单/新文档中的相关内容
     - LLM 生成修改建议（新增子树/修改门/废弃节点）
  4. 输出: diff 报告（新增/修改/删除的节点列表）

输出:
  - 修改建议列表（待专家审核）
  - diff 可视化（新旧对比高亮）
```

### 5.2 前端 diff 对比

- 在 ReactFlow 编辑器中高亮变化：
  - 🟢 新增节点（绿色）
  - 🟡 修改节点（黄色）
  - 🔴 建议删除节点（红色虚线）
- 专家逐项审核：接受 / 拒绝 / 修改每个建议

## 阶段六：评估指标体系

**目标**：提供可量化的系统评估，增强答辩说服力。

### 6.1 自动计算指标

| 指标 | 计算方式 | 展示位置 |
|------|----------|----------|
| 工单覆盖率 | 生成树的基本事件覆盖了多少历史工单故障 | 树详情页 |
| 结构指标 | 节点数、树深、门类型分布 | 树详情页 |
| 一致性评分 | 同一设备多次生成的结构相似度 | 评估报告 |
| AI/专家贡献比 | auto_generated 节点占比 | 树详情页 |
| 本体对齐率 | 有 ontology_ref 的节点占比 | 树详情页 |

### 6.2 API

| 方法 | 路径 | 功能 |
|------|------|------|
| GET | `/api/fault-trees/:id/metrics` | 获取单棵树的评估指标 |
| GET | `/api/metrics/comparison` | 多棵树对比报告 |

## 实施顺序与依赖关系

```
阶段一（工单数据基础）
    │
    ├──→ 阶段二（故障本体）  ←── 可并行，无硬依赖
    │         │
    │         ↓
    └──→ 阶段三（自动构建） ←── 依赖阶段一+二
              │
              ├──→ 阶段四（证据链追溯）
              │
              ├──→ 阶段五（增量更新）
              │
              └──→ 阶段六（评估指标）
```

**推荐实施顺序**：

| 优先级 | 阶段 | 原因 |
|--------|------|------|
| P0 | 阶段一 1.1-1.2（工单模型+导入） | 数据基础，后续全部依赖 |
| P0 | 阶段一 1.3（图谱增强） | 复用现有 GraphExtractionSkill，改动小 |
| P1 | 阶段二（故障本体） | 配置文件即可启动，无需大量开发 |
| P1 | 阶段三（自动构建核心流程） | **项目核心亮点**，工单驱动的故障树 |
| P2 | 阶段四 4.1-4.2（证据链） | 增强可信度，答辩加分项 |
| P2 | 阶段六（评估指标） | 数字化展示效果 |
| P3 | 阶段四 4.3（节点级AI操作） | 锦上添花 |
| P3 | 阶段五（增量更新） | 独立亮点但非必须 |

## 与现有系统的兼容策略

- **对话模式保留**：现有的对话式故障树生成不删除，作为"快速模式"
- **新增工单模式**：作为"专业模式"，入口独立
- **复用组件**：
  - ReactFlow 编辑器 → 直接复用，扩展节点属性面板
  - GraphExtractionSkill → 扩展 schema 后复用
  - ExpertLearningUseCase → 审核保存后自动触发
  - ContextManager → 自动构建各阶段的上下文编排复用
- **数据库迁移**：SQLite 新增 `work_orders` 表 + `fault_tree_nodes` 表加字段
